# Architecture & Security

How the game is put together, why it is safe, and how to extend it. Companion docs:
[UI_UX_GUIDE.md](UI_UX_GUIDE.md) (interface) and [ART_BIBLE.md](ART_BIBLE.md) (3D art bible).

---

## 1. The five non-negotiable rules and where they are enforced

| Rule | Enforcement |
|---|---|
| **Never trust the client; no `loadstring`** | The client sends only `(slot, source)` strings, enum-validated ids and slot numbers (`Shared/Net/RemoteSchema` + `Validate` + per-player rate limits in `Server/Services/NetService`). The server **re-compiles** every program with `Shared/DroneScript/Parser` and gates every construct with `Tech.isFeatureUnlocked` built from the **saved** `techUnlocks`. `import` and `simulate()` read **saved** script slots, never client text. The Interpreter walks a data AST and can only call the whitelisted builtins, so no Lua code is ever created. |
| **Async, never time out** | Each run is a `task.spawn` thread. The Interpreter yields every `YieldEvery` (100) steps via `task.wait(YieldEvery / StepsPerSecond)`, which caps CPU per player at 2,000 steps/s regardless of the code, so `while True: pass` can't stall the server. Every drone action waits its duration (`task.wait`). There are also idle-step, call-depth, memory and string limits. |
| **Session-locked data** | `Server/Data/SessionStore` (custom ProfileService equivalent: UpdateAsync-only, lock with a stale timeout, lost-lock kick, coalesced saves, BindToClose release) wrapped by `Server/Services/DataService`. Currencies, Tech unlocks, scripts, slot names and cosmetics live in **one record**, so they're written atomically. |
| **ProcessReceipt only after save** | `Server/Monetization/ReceiptProcessor`: dedupe by PurchaseId, apply the grant and record the PurchaseId with no yields in between, then `SaveAsync`, and **only then** `PurchaseGranted`; any failure returns `NotProcessedYet`. `ReceiptService` is the single assignment of the callback. |
| **Anchored drone, TweenService only** | The server never moves parts; it publishes the drone's cell and move duration as plot attributes. `Client/Controllers/PlotRenderer` tweens anchored, non-colliding parts (CFrameValue/NumberValue tweens composed with `BulkMoveTo`). Artist assets are forced inert by `Client/Visuals/AssetLibrary`. Plots are drawn in LOD tiers (NEAR full / MID 2-part drone + 1 part per tile / FAR nothing; own plot always NEAR); only NEAR drones are composed per frame or run infinite tweens. |

*Why not tween on the server?* A server tween replicates a CFrame update for every drone,
every frame, to every player. That's heavy on bandwidth and looks jittery. Publishing one
attribute per action and letting each client tween locally is smooth for everyone, and the
server stays authoritative over *where* the drone is.

## 3. Walkthrough: the life of `while True: move_up()`

```
CLIENT                                   SERVER
TerminalController.run()
 ├─ Parser.compile(source, limits,       (instant local feedback only)
 │    clientUnlocks)  -- same shared code
 └─ Net.invoke("RunScript", slot, source) ──► NetService.admit()
                                              ├─ player still in game?
                                              ├─ global + per-remote token buckets
                                              └─ Validate.args: slot ∈ 1..3, source ≤ 12,000 B, UTF-8
                                             ScriptService RunScript handler
                                              ├─ DataService:SetScript (keep the player's work)
                                              ├─ Parser.compile(source, limits(maxLines),
                                              │     unlockCheck(player))   ◄── SAVED techUnlocks
                                              │     'while' → requireFeature("while")
                                              │     locked? → CompileError "You haven't unlocked
                                              │       'while' loops yet. Research Loops
                                              │       "while True:" (Core) ..."  → back to client
                                              └─ startRun → task.spawn(...)
                                                   Interpreter.run(AST, ctx)
                                                    ├─ step() each statement / pass / call
                                                    │    every 100 steps → ctx.yield()
                                                    │      = task.wait(100 / 2000)   (CPU cap)
                                                    └─ move_up() → DroneAPI (LiveWorld)
                                                         ├─ GridService:CanMove (edges)
                                                         ├─ spend energy × throttle
                                                         ├─ GridService:MoveDrone
                                                         │    SetAttribute("DroneMoveTime", d)
                                                         │    SetAttribute("DroneX"/"DroneY", numbers)
                                                         │    SetAttribute("Drone", Vector3 x,y,0)
                                                         │    SetAttribute("DroneSerial", n+1)
                                                         │    FireAll("DroneMoved", index, x, y, d)
                                                         └─ task.wait(d)   (action delay)
PlotRenderer (every client)  ◄── DroneMoved remote + attributes + per-frame poll
 └─ TweenService:Create(move CFrameValue, d × 0.85, Quad InOut) + tilt tween
    RenderStepped: compose tweened values → PivotTo + workspace:BulkMoveTo(anchored parts)
```

**One driver per player** (`Server/DroneRuntime/RunGate`). STOP, leaving or a new RUN sets
`run.cancelled` **and `task.cancel()`s the run's thread**. The thread is always suspended at
that moment (in an action's wait, the CPU throttle or `simulate()`), and every builtin applies
its effect before its wait, so nothing is left half-done. A new run starts only once no other
run drives the drone: a hard mutex with no timeout. Cooperative cancel stays as a backstop:
`LiveWorld.wait` sleeps in 0.1 s slices and returns as soon as the run is cancelled, and
`SimWorld.wait` checks cancel and yields (`task.wait()`) every virtual second, so even a 600 s
`simulate()` can't hitch the server or outlive a Stop. `tests/spec/RunGate.spec.luau` replays
the race: a run busy in `simulate()` is killed by a second RunScript, and only one program's
harvest reaches the data.

## 4. The language and its Tech Tree gates

| Feature | Syntax | Gate (node) |
|---|---|---|
| loops | `while cond:`, `repeat 5 times:` | `loops` (Core) |
| crops | `plant("wheat")` ... `plant("cactus")` | `wheat`, `carrots`, `trees`, `sunflowers`, `pumpkins`, `cacti` |
| water | `water()`, `get_water()` | `water_tanks` |
| dig | `dig()` (bare soil only; the tile is exhausted ~25 s after every dig) | `fossils` |
| output | `print(a, b, ...)` | free from the start (debugging is not prestige) |
| throttle / clock | `set_speed(0.5..2)`, `get_time()` | `set_speed`, `get_time` |
| simulation | `simulate("lab", seconds)` | `simulate` |
| math | `+ - * / // %`, unary `-` | `math` |
| coordinates | `get_x()`, `get_y()`, `get_size()` | `coordinates` |
| variables | `a = 2`, `+= -= *= /=` | `variables` |
| lists | `[1, 2]`, `x[i]`, `in`, `len()`, `range()`, `for x in ...:`, `.append() .pop()` | `arrays` |
| functions | `def f(a):`, `return` | `functions` |
| dictionaries | `{k: v}`, `.keys() .values() .get()` | `dictionaries` |
| modules | `import utils`, `utils.f()` | `import` |
| randomness | `random()` | `random` |
| costs | `get_cost("carrots")` → dict | `get_cost` |

**Puzzle crop:** a pumpkin only ripens inside a complete 2 x 2 of fully grown pumpkins, and the
whole square ripens together (`Progression/Growth.settleSquares`, run by both the live tick and
`SimWorld`). A lone pumpkin grows to full size but `can_harvest()` stays False; harvesting
one from a forming square destroys it, and the other three keep waiting for a replanted fourth.

Free from the start: movement, `plant`/`harvest`, `if/elif/else`, comparisons,
`and/or/not`, `can_harvest`, `is_empty`, `charge`, `deposit`, `refine`, `get_battery`,
`get_cargo`, `get_weather`, `None`.

**Runtime limits** (`GameConfig.Script`):
* 2,000 steps/s CPU budget; 20,000 steps without a drone action is a "stuck loop" error.
* Recursion depth 32.
* 1,000 items per list/dict and 5,000 reachable items in total (a bounded reachability scan
  runs every 1,000 created items).
* Strings built at runtime are capped at 200 characters; numbers must stay finite and within
  1e15.

**`import utils`:** resolves the slot whose saved name is `utils`, compiles that slot's
**saved** source with the same gate, runs its top level once in its own module namespace, and
binds it. Import cycles (including importing yourself) are detected. Errors inside a module
are reported as "In 'utils', line 3: ...".

**`simulate("lab", 60)`:** runs the saved `lab` slot on a **SimWorld**, a copy of your current
field with a full battery and an empty hold, on a virtual clock. Actions advance virtual time
and grow crops instantly through the same `Growth` rules. It can't touch DataService, so it can
never grant anything. It's still CPU-throttled (same yield) and capped at 100,000 steps and
600 virtual seconds. It returns the number of items harvested. Simulations can't nest.

## 5. Data (schema v3)

```
PlayerData {
  schemaVersion = 3
  currencies    { hay, wheat, carrot, wood, sunflower, pumpkin, cactus, fossil, biomass, biofuel, batteries }
  techUnlocks   { [nodeId] = true }
  cargo         { [rawCurrencyId] = count }        -- the drone's hold, saved
  factoryBuffer, cropsHarvested
  scripts       { string × 3 }                     -- terminal slots
  scriptNames   { "main", "utils", "lab" }         -- module names for import / simulate
  cosmetics     { owned = { [id] = true }, equipped = { paint, hat } }
  boosts, oneTimeClaims, firstJoin, tutorial { step, done }, receipts
  field         { savedAt, tiles = { {x, y, crop, state, progress, watered, bareTime}, ... } }
}
```

* **The field size isn't stored**; it's derived from Grid Expansion research
  (`Tech.stats().gridSize`) and applied live by `GridService:Resize`.
* **The field's tiles are** (v3, `Progression/FieldSave`): `DataService:OnBeforeSave` lets
  GridService write a fresh snapshot right before every autosave, leave and shutdown, and
  `createPlot` restores it. No growth ticks are replayed: after more than 2 hours away,
  growing crops come back fully grown (ready; pumpkins through their 2 x 2), otherwise the
  field resumes exactly as it was. **Migration 2 → 3** gives old saves an empty field.
* **Migration 1 → 2** (`Sanitize`): every researched v1 node is **refunded in full** from a
  frozen v1 cost table, `techUnlocks` is cleared (no v1 id exists in v2, so no unlock ever
  appears without its prerequisites), `gridSize` is dropped, and names and cosmetics are filled
  with defaults. It's idempotent: v2 data is never refunded twice.
* **Transactions** are all non-yielding, validated before any change, and stored in the same
  record:
  * research: pay the full multi-currency cost and record the unlock (`Tech.research`)
  * cosmetics: deduct Lithium Batteries and record ownership (`Progression/Cosmetics`)
  * receipts: grant the reward and record the PurchaseId (`ReceiptProcessor`)

  A crash therefore persists both halves of a transaction or neither.
* **Lifecycle** (`DataService`): load (session lock, retries; kick on failure, never play on
  unsaved data), then autosave every 90 s, release on leave, and release everyone in parallel
  in BindToClose. A lost lock kicks the player (stops dupes).

## 6. Extending the game

**New crop**
1. Add the raw currency to `Config/Currencies.luau` (colour + glyph).
2. Add the crop to `Config/CropConfig.luau` (`currency`, `growSeconds`, `yield`, `shape`,
   `color`).
3. Add its `BiomassPoints` in `GameConfig.Factory`.
4. Add a Tech node with `unlocks = { "crop:<id>" }`.
5. Optionally add artist models under `Assets/Crops/<id>/<stage>`.

`Tech.validate()` (run by the tests and at server start) refuses the change if the currency has
no source or Factory value, or if any cost becomes unreachable.

**New Tech node:** add an entry to `TechTree.List` with `branch`, `tier`, `lane`, `requires`,
`cost` and `unlocks`/`stats`. The graph UI lays it out automatically. Update
`tests/spec/TechTree.spec.luau` if it changes the designed hierarchy.

**New builtin:** add its signature to `DroneScript/Builtins.luau` and its implementation to
`DroneRuntime/DroneAPI.luau` (using only `world:*`). Gate it by listing the name in a node's
`unlocks`.

**New Developer Product:** add it to `MonetizationConfig.Products` with declarative `grants`
plus display metadata, and paste its real id. `ReceiptProcessor` validates the grant at
startup.

### Studio playtest checklist (needs a real Studio session)

1. **Join:** the main menu shows with blur and a camera orbit. PLAY says "LOADING YOUR FARM..."
   until data loads.
2. **Starter flow:** a 3 x 3 field of wild grass. RUN the starter script and Hay appears in the
   **top-right** HUD after the drone lands on the charger.
3. **Gate:** typing `a = 2` and pressing RUN gives an error naming *Variables "a = 2"*.
   Research `loops` (9 Hay), then `wheat`, and `plant("wheat")` works. The tutorial coach walks
   a new player through exactly this (UI guide §5a).
4. **Grid Expansion I:** the field grows to 4 x 4 instantly, and existing crops don't move.
5. **Endless farm loop:** a `while True:` loop runs for minutes. The MicroProfiler / Script
   Performance shows low, flat activity, and STOP stops it within one action.
6. **Modules:** rename slot 2 to `utils`, define `def go(): move_up()`, then `import utils` and
   `utils.go()` from `main`.
7. **simulate:** `print(simulate("lab", 60))` prints a number and the real field is unchanged.
8. **Shop:** prompts open with real prices (once ids are set). A test purchase toasts only
   after the server saved it. Gamepass cards flip to OWNED.
9. **Hangar:** research Paint Shop, equip "Meadow", and the drone recolours for everyone.
10. **Rejoin:** currencies, research, all three scripts, slot names and cosmetics persist.

### Before publishing

* Paste real ids into `MonetizationConfig` (every `id = 0` shows "COMING SOON" and is never
  granted).
* Enable "Studio Access to API Services" to test real DataStores; otherwise the
  `MockDataStore` is used and a loud warning is printed.
